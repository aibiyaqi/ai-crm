## Bug 4：KeyError: 'tool_calls'

**现象**：
```python
KeyError: 'tool_calls'
```

**位置**：[`llms.py`](AI_CRM/llms.py) 的 `invoke()` 方法

**原因**：
`dashscope` 返回的 `assistant_message` 对象中，`hasattr(message, 'tool_calls')` 返回 `True`，但实际通过 `message.tool_calls` 访问时触发 `KeyError`。这是因为 dashscope SDK 用 `__getattr__` 做了代理，属性存在但值为空时也会报错。

**修复**：
```python
# 错误写法
if assistant_message.tool_calls:
    result["tool_calls"] = [...]

# 正确写法：用 try/except 兜底
try:
    if assistant_message.tool_calls:
        result["tool_calls"] = [...]
except (AttributeError, KeyError, TypeError):
    pass  # 没有 tool_calls 时静默跳过
```

## Bug 5：RAG 嵌入模型下载失败（网络不通）

**现象**：
```python
We couldn't connect to 'https://huggingface.co' to load this model.
```

**位置**：[`rag_law.py`](AI_CRM/rag_law.py) — `HuggingFaceEmbeddings` 初始化

**原因**：
`sentence-transformers` 库需要从 `huggingface.co` 下载 `all-MiniLM-L6-v2` 模型（约 80MB），但 WSL（中国区网络）无法连接 HuggingFace。

**修复方案（二选一）**：

### 方案 A：使用 HuggingFace 镜像站（临时方案）
```bash
export HF_ENDPOINT=https://hf-mirror.com
```

### 方案 B：改用通义千问 text-embedding-v2 API（推荐方案 ✅）
替换为 dashscope 的 TextEmbedding API，零下载、零本地存储：
```python
from dashscope import TextEmbedding

class QwenEmbeddings:
    """通义千问文本嵌入模型封装"""
    
    def __init__(self, model: str = "text-embedding-v2"):
        self.model = model
    
    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        resp = TextEmbedding.call(model=self.model, input=texts)
        return [item.embedding for item in resp.output.embeddings]
    
    def embed_query(self, text: str) -> list[float]:
        resp = TextEmbedding.call(model=self.model, input=[text])
        return resp.output.embeddings[0].embedding
```

## Bug 7：`'AddableValuesDict'` 对象没有属性 `'response'`

**现象**：
```
🤖 AI：❌ 处理出错："AddableValuesDict"对象没有属性"响应"
```

**位置**：[`agent.py:398-402`](AI_CRM/agent.py:398)

**触发链路**：
```
app.py:354 workflow.run() → agent.py:398 graph.invoke(initial_state)
→ agent.py:402 return final_state.response  ← 💥 报错
```

**根因**：
LangGraph 1.x 的 `invoke()` 返回的是**普通 `dict`**（不是 `AddableValuesDict`，也不是 Pydantic BaseModel），
而代码用 `final_state.response`（属性访问）而非 `final_state["response"]`（字典键访问），
`dict` 对象不支持属性访问，抛出 `AttributeError`。

**修复**：
在 [`agent.py:398-402`](AI_CRM/agent.py:398) 改用 `dict.get()` 取值：
```python
final_state = self.graph.invoke(initial_state)
response = final_state.get("response", "")
```

## Bug 8：Function Calling 工具定义未传给 LLM

**现象**：
```
[`tools.py`](AI_CRM/tools.py) 中定义了 web_search 和 sql_query 两个工具的 Function Calling 定义，
但 LLM 从未收到 tools 参数，导致工具形同虚设
```

**位置**：[`agent.py:326-329`](AI_CRM/agent.py:326)

**根因**：
[`_node_generate_response`](AI_CRM/agent.py:326) 调用 `self.llm.invoke(messages)` 时没有传入 `tools` 参数，
导致 LLM 不知道有工具可用，永远走直接回答路径。

**修复**：
在 [`agent.py:326-370`](AI_CRM/agent.py:326) 中实现两轮调用模式：
1. 第一轮：`self.llm.invoke(messages, tools=tool_defs)` — 传入工具定义
2. 如果 LLM 返回 `tool_calls`，执行工具并将结果追加到 `messages` 中
3. 第二轮：`self.llm.invoke(messages)` — 无 tools 参数，利用 tool 角色消息生成最终回答

```python
# 第一轮：调用 LLM，传入工具定义
response = self.llm.invoke(messages, tools=tool_defs)

# 检查 LLM 是否调用了工具函数
tool_calls = response.get("tool_calls")
if tool_calls:
    # 执行每个工具调用，并将结果加入对话
    for tc in tool_calls:
        func = tc["function"]
        tool_result = registry.execute(func["name"], json.loads(func["arguments"]))
        messages.append({"role": "tool", "content": str(tool_result), "name": func["name"]})
    # 第二轮：工具结果反馈给 LLM
    response = self.llm.invoke(messages)
```

## RAG 优化记录（2026-07-02）

**背景**：原有 RAG 系统存在 4 个问题——① 意图识别仅靠关键词规则，无法处理冷门查询；② BM25 分词用简单正则，中文无效；③ 嵌入模型依赖在线 API，网络不稳定时回退零向量；④ 固定 TopK 返回低质量结果时无法过滤。

**优化方案**（4 项，全部实施）：

---

### 优化 1：LLM 语义意图分类（方案B）

**文件**：[`AI_CRM/agent.py:214-331`](AI_CRM/agent.py:214)

**改动**：在规则匹配（阶段1）的基础上，新增 LLM 语义分类作为阶段2兜底。

**核心实现**：
```python
# 阶段1：规则匹配（零成本）
intent = self._rule_based_intent(query)
if intent:
    return {"intent": intent}

# 阶段2：LLM 语义分类（带 LRU 缓存）
cache_key = hashlib.md5(query.encode()).hexdigest()
if cache_key in self._intent_cache:
    return {"intent": self._intent_cache[cache_key]}
# 调 LLM 分类...
self._intent_cache[cache_key] = intent
return {"intent": intent}
```

**效果**：常见查询零延迟通过规则匹配；冷门查询由 LLM 精准兜底。LRU 缓存（max 200 条）避免重复 API 调用。

---

### 优化 2：jieba 中文分词（方案C）

**文件**：[`AI_CRM/rag_law.py:816-860`](AI_CRM/rag_law.py:816)

**改动**：将 `_tokenize` 从简单正则 `re.findall(r'\w+', text.lower())` 替换为 jieba 精确模式分词 + 停用词过滤。

**核心实现**：
```python
def _tokenize(self, text: str) -> List[str]:
    """jieba 中文分词 + 停用词过滤"""
    tokens = jieba.lcut(text)  # 精确模式分词
    stop_words = {"的", "了", "是", "在", "和", "有", "不", "就", "也", ...}
    # 过滤停用词 + 空白
    return [t.strip() for t in tokens if t.strip() and t.strip() not in stop_words]
```

**效果**：原正则分词将"退换货流程"视为一个 token，jieba 切分为 `["退换货", "流程"]`，显著提升中文 BM25 命中率。

### 优化 3：本地 BGE 嵌入模型（方案A）

**文件**：[`AI_CRM/rag_law.py:73-174`](AI_CRM/rag_law.py:73)

**改动**：新增 `BGEEmbeddings` 类，使用 `BAAI/bge-small-zh-v1.5`（~33MB）本地模型，替换 DashScope 在线 API 作为主嵌入方案。

### 优化 4：相关性阈值 + 自适应 TopK（方案D）

**文件**：[`AI_CRM/rag_law.py:585-750`](AI_CRM/rag_law.py:585)

**改动 A - 相关性阈值过滤**：在 `hybrid_search` 中，重排序后对分数低于 `RETRIEVAL_SCORE_THRESHOLD=0.5` 的结果进行过滤，至少保留 1 条结果兜底。

**改动 B - 自适应 TopK**：新增 `adaptive_search` 方法，动态分析相邻分数的下降幅度：

```python
def adaptive_search(self, query: str) -> List[str]:
    """自适应 TopK：基于分数分布动态截断"""
    results = self.hybrid_search(query, k=ADAPTIVE_TOP_K_MAX)
    if len(results) <= ADAPTIVE_TOP_K_MIN:
        return results  # 结果太少，直接返回
    
    cut = ADAPTIVE_TOP_K_MAX
    for i in range(1, len(results)):
        prev_score = results[i-1][1]
        curr_score = results[i][1]
        # 分数下降 > 50% 或低于阈值时截断
        if prev_score > 0 and (prev_score - curr_score) / prev_score > 0.5:
            cut = max(i, ADAPTIVE_TOP_K_MIN)
            break
    return [doc for doc, _ in results[:cut]]
```

**效果**：告别固定返回条数——检索质量好时多返回（最多6条），质量差时少返回（最少1条），有效提升 LLM 输入质量。

### P1-1：SQL Agent 6 层防注入（重要·安全）

| 层级 | 检查项 |
|------|--------|
| 1️⃣ | SELECT 开头检查 |
| 2️⃣ | 危险关键字黑名单（DROP/ALTER/DELETE/INSERT 等 12 个） |
| 3️⃣ | 多语句检测（分号 `;`） |
| 4️⃣ | SQL 注释检测（`--` 和 `/* */`） |
| 5️⃣ | 系统表保护（`sqlite_*`） |
| 6️⃣ | 字符串字面量剥离后检查关键字 |

**效果**：纵深防御，极大降低 SQL 注入风险。
